# SchemeBridge — Complete Mock Data Audit

## 1. Executive Summary

This audit provides a comprehensive investigation of static and mock data usage across the SchemeBridge codebase (`schemeBridge-frontend` and Java microservices integration).

- **Current State**: SchemeBridge is currently a **HYBRID** application.
- **Backend API Integration**: The authentication service (`auth-service`), OTP verification, API Gateway routing, and basic HTTP client layers (`apiClient.js`) are fully integrated with backend endpoints (`/api/v1/auth/*`, `/api/v1/schemes/*`, `/api/v1/documents/*`, `/api/v1/applications/*`, `/api/v1/notifications/*`).
- **Mock / Local Storage State**: Due to offline development and testing, several features initialize state from pre-defined mock datasets (`mockSchemes.js`, `mockDocuments.js`, `mockNotifications.js`, `mockProfile.js`, `mockRecommendations.js`, and embedded arrays in `AppContext.jsx`) and persist updates to `sessionStorage` and `localStorage`.

## 3. User-Side Mock Data Audit

### 3.1 Authentication & Session
- **Data Source**: **HYBRID** (Real API + Development Mocks).
- **Backend API**: Calls `/api/v1/auth/login` and `/api/v1/auth/register` on `auth-service` (Port 8081).
- **Mock Bypass**: In development mode or when entering `admin@gmail.com` / `admin`, `AuthContext.jsx` returns mock user object `ADM-001` with `super_admin` role. OTP `123456` is intercepted for instant dev verification in `authService.js`.
- **Session Storage**: User token and session state stored in `sessionStorage` (`schemebridge_user`, `schemebridge_token`).

### 3.2 User Dashboard (`/dashboard`)
- **Data Source**: **HYBRID / LOCAL STATE**.
- **User Profile & Stats**: Profile attributes read from `sessionStorage` / `localStorage` (`schemebridge_profile_<email>`).
- **Counts & Metrics**: Scheme match count, active application count, document readiness score, and unread notifications count are calculated dynamically from `AppContext` state.

### 3.3 Citizen Profile (`/profile`)
- **Data Source**: **LOCAL STORAGE / API FALLBACK**.
- **Attributes**: Full Name, Email, DOB, Gender, Occupation, Income, Caste, State, District, Pincode.
- **Storage**: Initialized from `user` session object, synced to `localStorage` key `schemebridge_profile_<email>`. `profileService.js` provides REST API methods `/api/v1/citizen/profile` with fallback to `localStorage`.

### 3.4 Matching Schemes (`/recommendations`)
- **Data Source**: **HYBRID** (`mockSchemes.js` + Client Eligibility Engine).
- **Scheme List**: Read from `schemes` array in `AppContext` (initialized from `mockSchemes.js`).
- **Match Engine**: `eligibilityEngine.js` executes local rule matching in the browser against user age, income, caste, state, and occupation.
- **AI Recommendation Badges**: Sourced from `mockRecommendations.js`.

### 3.5 Scheme Details (`/schemes/:id`)
- **Data Source**: **HYBRID** (`mockSchemes.js` + `mockRecommendations.js`).
- **Scheme Content**: Name, Ministry, Description, Benefits, Eligibility, Steps, FAQs read from `mockSchemes.js`.
- **AI Opportunity Score & Fit Explanation**: Generated by `getSchemeRecommendationDetails()` in `mockRecommendations.js`.

### 3.6 Document Vault (`/documents`)
- **Data Source**: **HYBRID / LOCAL STORAGE**.
- **Initial Data**: `DEFAULT_DOCUMENTS` from `mockDocuments.js`.
- **Persistence**: User uploads, deletions, and DigiLocker imports are saved to `localStorage` key `schemebridge_documents_<email>`.
- **Backend API**: `documentService.js` connects to `/api/v1/documents/me` (Port 8082). If backend is offline or `VITE_USE_MOCK_API=true`, operates on local storage sandbox.

### 3.7 Application Tracker (`/tracker`)
- **Data Source**: **HYBRID / LOCAL STORAGE**.
- **Initial Data**: `DEFAULT_APPLICATIONS` embedded array in `AppContext.jsx` (APP-9023, APP-1042, APP-5120).
- **Live Sync**: Submitting an application adds a record to `applications` in `AppContext`. When Admin updates status (`Approved`, `Rejected`, `Preparing Documents`) in `AdminDashboard`, state updates in real-time and persists to `localStorage` key `schemebridge_applications`.

### 3.8 Notifications (`/notifications`)
- **Data Source**: **HYBRID / LOCAL STORAGE**.
- **Initial Data**: `DEFAULT_NOTIFICATIONS` from `mockNotifications.js`.
- **Live Sync**: Admin actions emit real-time notifications via `addNotification()` in `AppContext`, saved to `localStorage` key `schemebridge_notifications`.

### 3.9 Help & Support (`/help`)
- **Data Source**: **HYBRID / LOCAL STORAGE**.
- **Initial Data**: `DEFAULT_GRIEVANCES` embedded array in `AppContext.jsx` (GRV-7401, GRV-5219).
- **Submission**: Grievances submitted by citizens add records to `grievances` state and persist to `localStorage` key `schemebridge_grievances`.

## 4. Admin-Side Mock Data Audit

### 4.1 Admin Dashboard Overview (`/admin/dashboard` - Overview)
- **Data Source**: **LOCAL STATE CALCULATION**.
- **KPI Cards**: Total Users, Active Applications, Pending Review, Grievances, Scheme Directory count calculated directly from `AppContext` arrays (`applications`, `grievances`, `usersRegistry`, `schemes`).

### 4.2 Admin Applications Management (`/admin/dashboard` - Applications)
- **Data Source**: **HYBRID / LOCAL STORAGE**.
- **Data**: Reads `applications` from `AppContext` (initial data: `DEFAULT_APPLICATIONS`).
- **Actions**: Approve, Reject, and Request Documents call `updateApplicationStatus()` in `AppContext`, which updates application stage and creates targeted user notifications.

### 4.3 Admin Grievances Desk (`/admin/dashboard` - Grievances)
- **Data Source**: **HYBRID / EMBEDDED COMPONENT MOCK**.
- **Grievance Records**: Sourced from `grievances` in `AppContext` (initial data: `DEFAULT_GRIEVANCES`). Clicking **Resolve** updates status to `RESOLVED` and dispatches notification.
- **Embedded Mock**: `GrievanceManagementDesk.jsx` contains hardcoded ticket discussion logs and timeline history for tickets `GRV-7401` and `GRV-5219`.

### 4.4 Admin User Management (`/admin/dashboard` - Users)
- **Data Source**: **EMBEDDED MOCK DATA**.
- **Data**: Initialized from `DEFAULT_USERS_REGISTRY` embedded in `AppContext.jsx` (citizens, officers, managers, support staff, admins). Persisted to `localStorage` key `schemebridge_users_registry`.

### 4.5 Admin Scheme Management (`/admin/dashboard` - Schemes)
- **Data Source**: **HYBRID**.
- **Data**: Sourced from `schemes` in `AppContext` (`mockSchemes.js`). Adding, editing, or deleting schemes mutates `schemes` state and updates audit logs.

### 4.6 Analytics & Reports (`/admin/dashboard` - Analytics & Reports)
- **Data Source**: **HARDCODED COMPONENT MOCK DATA**.
- **AnalyticsDashboard.jsx**: Contains hardcoded arrays for monthly application trends, category breakdown charts, state-wise application volumes, demographic distributions.
- **GovernmentReportsCenter.jsx**: Contains hardcoded report template options and mock generated report history.
- **AIOperationsSummary.jsx**: Contains hardcoded AI metrics (OCR Accuracy 98.4%, Triage Precision 96.2%, Prompt Latency 1.2s).

## 11. Critical Findings

1. **State Persistence Sandbox**: The application simulates a full stateful experience (application submissions, grievance resolution, document uploads, status changes) using `AppContext` React state and `localStorage` / `sessionStorage`. To an end user, the platform looks 100% live, but backend database persistence occurs primarily when `VITE_USE_MOCK_API=false` and microservices are active.
2. **Offline Resilience**: The frontend services (`authService.js`, `schemeService.js`, `documentService.js`, `applicationService.js`, `notificationService.js`) are designed with fallback routines so that if a Java microservice is down, the UI gracefully continues running using mock data.
3. **Dead Code**: `src/data/mockDashboard.js` is obsolete and can be safely archived or removed in future cleanup phases.

## 12. Recommended Next Steps (For Future Phases)

1. **Phase 4 Integration (Core & Application Microservice Sync)**: Connect `applicationService.js` and `schemeService.js` directly to `core-service` (Port 8082) so submitted applications write to Oracle DB table `APPLICATIONS`.
2. **Phase 5 Integration (Notification Microservice Event Ingestion)**: Wire `notificationService.js` to `notification-service` (Port 8083) to consume domain events (`APPLICATION_APPROVED`, `GRIEVANCE_RESOLVED`) directly from Kafka / Spring Cloud Bus.
3. **Clean Up Dead Mock File**: Remove or deprecate `src/data/mockDashboard.js`.

## 13. Conclusion

SchemeBridge is currently **HYBRID**. The authentication architecture and API client infrastructure are fully aligned with the Java Spring Boot microservices, while scheme discovery, document vault, application tracking, grievances, and notifications rely on centralized `AppContext` state backed by structured mock datasets (`mockSchemes.js`, `mockDocuments.js`, `mockNotifications.js`, `mockRecommendations.js`, `mockProfile.js`) for seamless development and offline testing.
